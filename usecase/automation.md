# usecase/automation.md — 自動化・業務効率化系の生成仕様

builder.md「用途判定とルーティング」でこの分類になった時**だけ**読む。
(判定キーワード: 自動化 / 毎朝 / 定期 / 処理 / 取得 / データ / API / スクレイプ / 通知 / 連携 / バッチ)

## スタック

- 言語: TypeScript(基本)/ Python(自然言語処理・データ分析が中心なら)
- 補助: tsx(TS の場合)/ venv(Python の場合)/ dotenv

### スタック上書き(ユーザー指定を優先)

- ユーザーが `aboutme.md` / `ai-behavior.md` で**自動化基盤を明示指定**している場合(例: 「自動化はなるべく n8n で作りたい」)は、上記スクリプト系デフォルトより**ユーザー指定を一次選択にする**
- **「ツールを使っている」という事実の記載だけでは明示指定とみなさない**(指示形の記述のみが上書き)。aboutme に役割分担の記載があればそれに沿って選ぶ(例: 「n8n = ワークフロー基盤 / Claude Code = 日常運用」なら、個人用の小さな自動化は Claude Code 側)
- **迷うグレーゾーンでは**: 選んだ方を設計書に載せ、**選択理由 + もう一方への切替オプションを 1 行で明示**する(黙ってどちらかに倒さない)
- 自動化基盤に **n8n** を使う場合の接続手順・ワークフロー構築の定石は `knowledge/n8n.md` を読んで成果物に焼き込む
- 指定が無ければ従来どおりスクリプト系デフォルト(過剰に外部基盤を持ち出さない)

## スキル構造

- `.claude/skills/{skill-name}/SKILL.md` — 指示書(必須)
- `.claude/skills/{skill-name}/run.ts` or `run.py` — 実行スクリプト(**必要時のみ**)
- **SKILL.md で完結する場合は run.* を作らない**(MCP / Claude API 内で完結するもの等)
- 重い処理は AI トークンではなくスクリプト(tsx / python)に逃がし、AI は判断だけにする(構造的に一番効くコスト対策)

## 定時実行(ルーチン)を伴う場合の追加要件

「毎朝メール」「毎日通知」のように Claude Code のルーチン(`/schedule`)で回す前提のプロジェクトを生成する時は、以下を最初から組み込む。**外部 cron / GAS / n8n に出すのはルーチン単独で不可能 or 不向きが判明してから**(ただしユーザーが上記「スタック上書き」で n8n 等を明示指定している場合はそれを優先)。(2026-06 検証)

1. **env の二重化**: `.env` / `.env.example` はローカル開発用。ルーチン用には同名キーを Cloud Environment の env として別途登録する手順を README に明記する(ローカルの `.env` はルーチンからは読まれない)
2. **接続先ホストの列挙**: 外部 API / Webhook を叩く場合、ネットワーク許可リストに入れるホスト名を README に列挙する(リダイレクト先ホストも別物として書く)
3. **MCP allowlist**: そのルーチンが必要とする MCP コネクタだけを許可する旨を README に書く(全許可で動かさない)
4. **冪等性ガード(送信・通知系プロジェクト必須)**: 送信履歴ファイル / dry-run フラグ / 「リダイレクトやリトライ可能エラーを失敗扱いしない」curl オプション固定 のいずれかをジョブ側にも実装する。**スケジューラ 1 回起動で複数通送る事故**を、プロンプトの注意書きだけに頼らず物理的に防ぐ
5. **プロンプトの 1-shot 制約**: ルーチンプロンプト(SKILL.md / `.claude/schedules/*.md` 等)に「送信は 1 回のみ。失敗してもリトライしない。重複より欠損を選ぶ」を明示する

あわせて `.claude/rules/scheduled-jobs.md`(`templates/rules-scheduled-jobs.md`)を配置する(builder.md「rules の配置」参照)。
