# usecase/assistant.md — AI 秘書・アシスタント系の生成仕様

builder.md「用途判定とルーティング」でこの分類になった時**だけ**読む。
(判定キーワード: 秘書 / 相談 / 伴走 / コーチ / 顧問 / 業務サポート / アシスタント)

## スタック

固定しない(コンテキスト主体のプロジェクト)。

## 初期構造

最小(CLAUDE.md + aboutme.md + ai-behavior.md + 空の `.claude/`)+ `automations.md`(自動化台帳、空。`templates/automations-registry.md` からコピー)+ 最初に依頼された機能のスキル(任意)。

**成長**: ユーザーが「ブランド資料を渡したい」「顧客情報を覚えてほしい」等と言ったら、AI が必要なフォルダ(例: `brand-assets/`、`context/`)を提案して作る。

## 自動化は「コピーせず台帳に登録」(2026-07 方式変更)

別途ビルダーで作った自動化プロジェクト(例: ニュースメール配信)は、**実体をコピーせず、秘書ルートの `automations.md`(台帳)に場所と呼び出し方を登録する**。実行時は登録された元の場所を `cd {場所} && claude -p "..."` で直接呼ぶ。

- **なぜコピーしないか**: コピーは元プロジェクトの更新から取り残されてズレる・`.env`(秘密)まで複製される・ディスクも食う。秘書に必要なのは「何がどこにあって、どう呼ぶか」のリストだけ
- 登録手順は `.claude/commands/import-automation.md` に固定(`templates/import-automation.md` からコピー)。「○○を取り込んで」とユーザーに言われたら、このコマンドのプロトコルに従う(**取り込む=台帳に登録する**。コピーではない)
- **旧方式(`automations/` フォルダへのコピー)の秘書をアップデートする時**: コピー済みフォルダは黙って消さない。「台帳方式へ移行できます(コピーを台帳登録に置き換え、実体は元プロジェクトを使う)」と提案し、ユーザーが選ぶ

### 台帳(automations.md)のエントリ形式

```markdown
## {name}
- 場所: {元プロジェクトの絶対パス or 秘書からの相対パス}
- できること: {1 行サマリ}
- 呼び出し方: `cd {場所} && claude -p "..."`(または `pnpm run send` 等)
- 目標・頻度(任意): {例: 平日 毎朝 1 回 / 月 8 本}
- メモ(任意): {最終実行日・注意点など}
```

## 目標(KPI)層 — 秘書の値打ちは「回数を決める」こと

ただ定時実行するだけなら cron で足りる。秘書の付加価値は**目標から逆算して、どの自動化を・いつ・何回回すかを決めて、進捗を報告する**こと。

- 台帳エントリの「目標・頻度」が KPI。ユーザーが目標を口にしたら(「ブログ月 8 本」等)、台帳の該当エントリに書き込む
- 「おはよう」等の起動時や報告時に、**目標 vs 実績を見て不足分から提案する**:「今月あと 3 本足りません。記事生成を今週 2 回回しますか?」
- ダッシュボード(あれば)の更新時にも、目標 vs 実績を 1 行反映する
- 目標が無いエントリは提案しない(押し付けない)

## 生成時にやること(AI 秘書系の追加要素)

1. `automations.md`(空の台帳)を配置(`templates/automations-registry.md` からコピー)
2. `.claude/commands/import-automation.md` を配置(`templates/import-automation.md` からコピー)
3. CLAUDE.md「できること」リストの下に **2 行のヒント**を追加:
   > 作った自動化を秘書から使いたい時は「○○を取り込んで」と話しかけてください(台帳 `automations.md` に登録されます。詳細: `@.claude/commands/import-automation.md`)
   > 新しい自動化をゼロから作りたい時は、この秘書では作らずビルダーで土台を作り、できたら上の手順で登録してください(秘書は「使う・育てる」担当、作るのはビルダーの担当です)

## automations のオーケストレーション(Subagents + モデル階層)

複数の automations を「おはよう」の一言で並列実行したい時の組み方。**Subagents(ファンアウト)を使う。Agent Teams は使わない**。(2026-06 検証)

- **なぜ Subagents か**: automations は各々独立(ニュース / 天気 / 電池など)、互いに通信不要、秘書が結果を束ねるだけ。これは「結果のみが重要な独立タスク」= Subagents の領分。Agent Teams(共有タスクリスト・メンバー間通信・各員が別 Claude インスタンス)は「議論・協力が必要な作業」用で、独立タスクに使うとトークンが高くつくだけ
- **構成**: 秘書本体(オーケストレーター)が `.claude/agents/{name}.md` の subagent を Agent ツールで並列 spawn。各 subagent は担当 automation を**台帳(`automations.md`)に登録された場所**へ `cd {場所} && claude -p "..."` で起動し、結果を秘書に報告。秘書が 1 枚に束ねて返す

### モデルは 3 レイヤーで決まる(混同しない・上から下に伝搬しない)

| レイヤー | model を決める場所 | 備考 |
|---|---|---|
| 秘書本体(束ねる・判断) | 秘書の `.claude/settings.json` | 例: opus |
| subagent 自身の判断 | `.claude/agents/{name}.md` の frontmatter `model:` | 「受けてスクリプトを叩く」だけなら haiku / sonnet |
| automations の AI 処理 | 元プロジェクト(台帳の「場所」)側の `.claude/settings.json` の `model` | **subagent が台帳の場所へ `cd` してから `claude -p` しないと効かない**(cd 無しだと秘書側設定が読まれる) |

frontmatter の `model:` は「その subagent の頭の良さ」だけを決める。subagent が叩く `claude -p` の先は automations 側の設定で決まる(別レイヤー)。

### モデル階層化はコスト戦略でもある

- 「全部 opus」より「opus 1 + haiku 複数並列」の方が速くて安い。これが automations を Subagents で回す旨み
- **コストが効くのは API 従量課金で動かす時**(特に定時実行で `claude -p` を繰り返すルーチン)。サブスク(Pro / Max)は月額上限で頭打ちなので「使いすぎ爆死」はまず起きない。従量で回す構成だけ、安いモデルへ寄せる設計が実利
- 重い処理は AI トークンではなくスクリプトに逃がし、AI は判断だけにする ── 構造的に一番効くコスト対策

### Fable 5(最上位帯)は「使う前に必ず確認」(2026-07 検証)

モデルの帯は上から **Fable 5(`claude-fable-5`)> Opus 4.8 > Sonnet 5 > Haiku 4.5**。Fable 5 は最難関・長期エージェント作業向けの最上位だが、**従量課金で入出力とも Opus の約2倍($10 / $50 per 1M)**。

- **既定は Opus のまま。Fable 5 を既定にはしない**(3 レイヤー表の「例: opus」を Fable に上げない)。
- **Fable 5 に切り替える時は、その前に必ず `AskUserQuestion` で一度確認する**:「これは従量課金で Opus の約2倍の単価です。Fable 5 で進めますか?」。ユーザーが明示的に「Fable で」と言った場合も、**従量で回る automation / 定時実行に組み込む時は**同じ確認を挟む(単発の対話利用は指名=同意でよい)。CONCEPT「事故らない/リミット」の柱に沿った、お金の歯止め。
- **API 挙動が違う点も申し送る**: thinking は常時オン(`budget_tokens` 不可)、安全分類器で `refusal` が返ることがある、**30日データ保持が必須**(ZDR 組織は全リクエスト 400)、**Fast mode は非対応**(Opus 4.8/4.7 のみ)。

**生成時**: automations を持つ AI 秘書を生成する時は、上記の指針(Subagents 採用・`cd` 必須・3 レイヤーのモデル指定・**Fable 5 は使用前確認**)を秘書の CLAUDE.md「振る舞い」か該当 subagent 定義に書き込み、秘書が実行時に迷わないようにする。

## ★ CLAUDE.md の書き方(AI 秘書系)

**「特定機能専用 AI」ではなく「{user 名} さんの AI 秘書、できることリスト」型で書く**。
理由: 後から機能を足した時に**リストに 1 行追加するだけ**で済む構造にする。最初の機能だけで人格を縛らない。

❌ **悪い例**(機能限定型 — 機能を足したら CLAUDE.md 全体を書き直す羽目になる):
```markdown
# 毎朝ブリーフィングAI秘書

このプロジェクトは「毎朝のブリーフィングメール」を作って Gmail へ送る AI 秘書です。
```

✅ **良い例**(キャラ + できることリスト型 — 機能追加に強い):
```markdown
# {project-name}

あなたは {user 名} さんの AI 秘書です。

## できること

1. **毎朝のブリーフィング生成・送信** — `.claude/skills/morning-briefing/`
   毎朝、6 つのソースから情報を集めて Gmail に送る
2.(機能が追加されたら、ここに 1 行追記する)

## 振る舞い

(共通の振る舞いルール、リビジョン保存、.env の扱いなど)

## このファイルの使い方(AI 向け)

- このファイルは **200 行以内**に保つ。秘書としての人格・できることリストの索引だけを置く
- 各機能の**フォーマット本体・手順・プロンプト・規約**は、適切な場所に切り出す:
  - 機能ごとの動作仕様 → `.claude/skills/{name}/SKILL.md`
  - 横断的なルール(コーディング規約、出力フォーマット等)→ `.claude/rules/{topic}.md`
  - その他、テンプレや資料 → 専用フォルダ
- CLAUDE.md には**1 行サマリ + 参照リンク**だけ追記する
- 200 行を超えそうな時は、内容を外部ファイルへ切り出してから CLAUDE.md からはリンクで参照する
```

**ポイント**:
- 冒頭は「**あなたは {user 名} さんの AI 秘書です**」(キャラ定義、機能で縛らない)
- 「できること」を**箇条書きのリスト**にする(機能追加で伸びていく前提)
- 各機能は**1 行サマリ + 参照先へのリンク**(詳細は SKILL.md / `.claude/rules/` 等に任せる)
- 機能追加時の指示も明記:「機能が追加されたら、ここに 1 行追記する」
- 「このファイルの使い方」ブロックを**生成 CLAUDE.md に必ず含める**(後の Claude にも 200 行ルールと切り出し方針が伝わるように)
