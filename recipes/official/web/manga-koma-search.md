# レシピ: 漫画 全コマ検索

> セリフ(キーワード)を打つと、その言葉が入った漫画のコマが画像一覧で出てくる Web アプリを、PDF 1 冊から再現する設計書。
> このレシピを自分のビルダーに読み込ませると、同じ構成・同じ作り方を再現できます。

- 製品名: 漫画 全コマ検索
- 用途分類: Web(静的サイト + Python データパイプライン)
- スタック: Python 3.12(PyMuPDF / OpenCV / manga-ocr / easyocr)+ 素の HTML/CSS/JS + 静的ホスティング
- 秘密情報: なし(OCR はローカル、公開は静的サイト。API キー不要)
- 必要ビルダー VERSION: 3.9.0 で実走
- 検証ステータス: `verified` — skeleton(骨組みのみ)/ experimental(未実証)/ verified(実ビルド結晶化済み)。verified だけが配布対象
- 動作確認: `mac ✅` / `win ✅` — 実機で建てて緑を取れた OS(mac=元の実ビルド / win=2026-06-27〜28 全ページ実走)
- 配布元検証: `✅` — 配布元(kote2)が win 実機で最終サインオフ(2026-06-27)

## 1. これは何 / 機能構成 + 完成形(受け入れ基準)

漫画 PDF 1 冊を「セリフで検索できるコマ画像の静的サイト」に変える 2 層構成。

```
data/raw/<your>.pdf
  ① PDF → ページ画像        (data/pages/)
  ② ページ → コマ画像        (web/data/panels/) + コマ一覧(panels_manifest.json)
  ②.5 コマ → テキスト領域検出  (manifest に regions を追記)
  ③ 領域 → セリフ OCR        (panels_ocr.json)
  ④ → 検索インデックス        (web/data/index.json) ← 検索サイトが読む
```

- **裏方 `pipeline/`(Python)**: ①〜④ の一回限りの下ごしらえ。一括は `run_all.py`、設定は `config.py`。
- **表 `web/`(素の HTML/CSS/JS)**: `index.json` をブラウザ内で検索する静的サイト。サーバー不要。

### 機能構成(★ここだけが必須/任意/不採用を決める正本。他章はこの表を参照する)

| ID | 機能 | 状態 | Phase | 完成判定 |
|---|---|---|---|---|
| CORE-01 | PDF → ページ画像 → コマ画像パイプライン(X-Y カット・読み順 上→下, 右→左・背景明暗の反転判定) | required | Phase 2/4 | PASS 必須 |
| CORE-02 | 文字領域検出(CRAFT)→ 領域単位 OCR(manga-ocr)(②.5 → ③) | required | Phase 2/4 | PASS 必須 |
| CORE-03 | 検索インデックス生成 + 静的検索サイト(部分一致・画像グリッド) | required | Phase 5 | PASS 必須 |
| FEAT-01 | コマクリックで拡大(モーダル) | optional-enabled | Phase 5 | enabled なら PASS 必須 |
| FEAT-02 | GPU 高速化(`easyocr.Reader(..., gpu=True)` で ②.5 を短縮) | optional-disabled | — | 既定 SKIP(**未検証**。CPU 実走のみ) |
| EXCL-01 | クラウド OCR(高精度化。鍵を扱う) | excluded | — | 別実装(§4 派生アーキ) |

## 2. スタック

| 層 | 採用 | 備考 |
|---|---|---|
| パイプライン | **Python 3.12**(venv) | ステップは数字始まり(`010_…`〜`040_…`)で **import できない**ため、`run_all.py` が subprocess で順に起動し、ファイル(pages / manifest / json)経由で受け渡す |
| PDF 描画 | **PyMuPDF**(fitz) | ページ → 画像 |
| 画像処理 | **OpenCV** | コマ分割(X-Y カット)。I/O は必ずバイト経由ヘルパ(§3-4 / §6-⑦) |
| 文字領域検出 | **easyocr**(CRAFT 検出器 `Reader.detect` 流用) | ②.5。処理時間の律速(§6-⑤) |
| OCR | **manga-ocr** | 日本語漫画専用・ローカル・無料・鍵不要 |
| 表(検索 UI) | 素の **HTML/CSS/JS** | `index.json` をブラウザ内で検索。サーバー不要 |
| 公開 | 静的ホスティング | `web/` 一式をそのまま載せる |

## 3. アーキの肝 = 魔法のタネ(★変えちゃダメ)

ここを崩すと精度・維持コストが別物になる。再現必須:

1. **2 層に分ける**: 重い下ごしらえは Python に隔離し、表示はブラウザ完結の静的サイトにしてサーバー維持コストをゼロに。
2. **③ の前に ②.5(テキスト領域検出 / CRAFT)を挟む**: manga-ocr にコマ全体を渡すと幻覚する(§6-②)。文字領域だけ検出して領域ごとに OCR し読み順に連結する。これが品質の肝。
3. **コマ分割は X-Y カット + 背景基準の中身判定**: 余白(ガター)で再帰分割。枠線つき・グリッド状のコマに強く依存が軽い。中身判定はページ外周の明度から背景の明暗を判定して反転させる(§6-①)。読み順は漫画向けに**上→下, 右→左**。
4. **画像 I/O は必ずバイト経由(`imdecode`/`imencode`)**: `cv2.imread`/`imwrite` は非 ASCII パスで黙って死ぬため、最初から共通ヘルパに隔離し全ステップで使う(§6-⑦)。
5. **ステップ間はファイル受け渡し(subprocess 直列)**: 各段の成果物が残るので、失敗時の部分再実行・目視検証がしやすい。

## 4. 改変の余地(★変えていい。状態=必須/任意は §1 表が正本)

### 軽量設定(設計を変えず差し替え。サイレント適用してよい唯一の層)

うまくいかない時に触る knob(§5 Phase 3 で使う調整表):

| うまくいかない | 触る所 | 方向 |
|---|---|---|
| 1 コマが細切れ | `config.MIN_GUTTER_PX` | 大きく |
| 複数コマが 1 枚に | `config.MIN_GUTTER_PX` | 小さく(※吹き出しが原因の時は §6-⑧) |
| 文字がかすれて読めない | `config.PAGE_DPI` | 大きく(重くなる) |
| テキストを拾いすぎ/取りこぼし | `025_detect_text.py` の `TEXT_THRESH`/`LINK_THRESH`/`CLUSTER_GAP_RATIO` | 様子を見て増減 |

ほか、検索サイトの配色・グリッド列数も軽量設定。

### 機能モジュール(ON/OFF で Phase とテストが増減。状態は §1 表)

- **FEAT-01 拡大モーダル**: 既定 ON。外すと一覧のみ(`[hidden]` の打ち消しを忘れない。§6-③)
- **FEAT-02 GPU 高速化**: 既定 OFF・**未検証**。GPU があれば ②.5(律速)が大幅短縮の見込み

### 派生アーキ(★knob ではない。魔法のタネだけ移植して別実装=実質「別レシピ」)

- **OCR をクラウド OCR に差し替え**(EXCL-01): 精度がもっと要る時だけ。ローカル完結・鍵不要という §1 の前提が変わる(その時だけ鍵を扱う)。提案 → ユーザー GO
- **検索をサーバ型(全文検索エンジン等)に**: 「静的サイト=維持ゼロ」の魔法(§3-1)を外す判断。同じく別レシピ相当

## 5. 再現の順路(Phase + 各段の検証)★最重要

**いきなり全ページ処理しない。** 試運転(Phase 2)で目視 → 調整 → 全ページ。

| Phase | やること | 検証(緑の条件) |
|---|---|---|
| 0 環境 | venv 作成 → `pip install -r pipeline/requirements.txt` | `fitz`/`cv2`/`manga_ocr`/`easyocr` が import できる |
| 1 投入 | PDF を `data/raw/` に置き、`config.WORKS` に作品を登録(`title`/`volume`/`pdf`/`slug`) | ファイル名と config が一致 |
| 2 試運転 [CORE-01 / CORE-02] | `python pipeline/run_all.py --pages <数> --start <本編開始p>` | コマ画像と `index.json` の OCR を**目視**で確認 |
| 3 調整 | `config.py`・`025_detect_text.py` のしきい値を直して再試運転(§4 軽量設定の表) | 分割・読み取りが実用域 |
| 4 全ページ [CORE-01 / CORE-02] | `python pipeline/run_all.py` | 全コマ生成・OCR 完了(**重い。§6-⑤**) |
| 5 体感 [CORE-03 + FEAT-01] | `python -m http.server -d web 8000` → ローカルで検索 | 狙った語が該当コマに当たる |
| 6 公開 | `web/` 一式を静的ホスティングへ | 本番 URL で動く(※§9 =明示の合図があってから) |

> ★Phase 2 の鉄則: 試運転は**本編が始まるページを含める**。前付け(表紙・目次・大ゴマ)だけだと、分割も OCR も評価を誤る(§6-⑥)。`010` に `--start` を持たせ本編から描けるようにしてある。

## 6. 固有の地雷 + 直し方(★実ビルドで踏んだ地雷を結晶化。ここが最大の資産)

各地雷は固定 ID(`PIT-{ドメイン}-{3桁}`)+ 確認環境 + 回帰を持つ([templates/recipe/recipe-template.md](../templates/recipe/recipe-template.md) の PIT 規約)。

1. **[PIT-CV2-XY-001] 黒背景ページでコマが丸ごと 1 枚になる** — 中身判定が「暗い=中身」固定で黒背景とミスマッチ。→ 各ページ外周の明度から背景の明暗を判定し、中身の定義を**反転**(暗背景→明るい画素=中身)。ガターが背景色なので背景基準にすれば切れ目が出る。
   確認環境: mac 実ビルド(2026-06)/ 回帰: 手動(黒背景ページの分割を目視)
2. **[PIT-OCR-001] manga-ocr にコマ全体を渡すと幻覚する**(無セリフのコマで実在しない文章を出す)。→ ③ の前に CRAFT で**文字領域だけ検出**し、領域ごとに OCR して読み順に連結。文字無し=空にする。モデルを本来の用途(吹き出し 1 つ)で使えるようになる。実走でも無セリフのコマはほぼ空に落ちた。
   確認環境: mac + win 実走(2026-06-27)/ 回帰: 手動(無セリフコマの OCR が空)
3. **[PIT-CSS-001] `hidden` のモーダルが起動時に開きっぱなしで画面が真っ暗** — クラスの `display:flex` が `hidden` 属性に優先度で勝つ。→ `.modal[hidden]{display:none}` を足す。JS で `hidden` 開閉する要素には `[hidden]` 打ち消しをセットで書く。
   確認環境: mac(2026-06)/ 回帰: TEST-003(§10 マトリクス)
4. **[PIT-WEB-PATH-001] 画像が表示されない(生成パスと配信ルートのズレ)** — 画像実体は `web/data/panels/` なのに索引の `img` が `data/` 抜けを指す。サイトは `web/` がルートなので 404。→ `img` はサイトルート基準(`data/panels/...`)で書く。実体解決はファイル名ベースにしてパス接頭辞に依存させない。
   確認環境: mac(2026-06)/ 回帰: 手動(検索結果のコマ画像が表示される)
5. **[PIT-OCR-002] 重い処理の時間 — 律速は OCR ではなく「②.5 文字領域検出(CRAFT)」** — win/CPU 実測(199p→630コマ, 合計 約3.3時間): ①ページ描画 約3.8分 / ②コマ分割 約3.7分 / **②.5 CRAFT 検出 約2.9時間(支配的)** / ③manga-ocr 約16分 / ④索引 即時。直感に反し OCR より**文字領域検出が桁違いに重い**(コマ全体に検出器をかけるため)。見積もりは正直に「**CPU なら数時間**」と伝える。GPU(`easyocr.Reader(..., gpu=True)`)があれば②.5は大幅短縮。試運転(十数ページ)はモデルDL込みで数分。
   確認環境: win CPU 実測(2026-06-28)/ 回帰: —(仕様。見積もりを正直に伝える)
6. **[PIT-PROC-002] 試運転ページの選び方** — 前付けだけで試すと本編の作り(背景色・コマ割り)を見ないまま判断してしまう。必ず本編を含める。
   確認環境: win 実走(2026-06-27)/ 回帰: 手動(試運転に `--start` で本編を含める)
7. **[PIT-CV2-IO-001]【win 地雷】`cv2.imread`/`imwrite` が非ASCIIパスで黙って失敗する** — Windows では cv2 がパスをロケール(CP932)で解釈し、日本語を含むパス(例: `デスクトップ`)のファイルを開けず **None を返す**(`!_src.empty()` で落ちる)。mac では出ない。→ 画像 I/O を `np.fromfile→cv2.imdecode`(読み)/ `cv2.imencode→tofile`(書き)のバイト経由ヘルパに統一し、全ステップでそれを使う。OS・パス文字に依存しなくなる(mac でもそのまま動く)。
   確認環境: win 実走(2026-06-27)/ 回帰: TEST-004(§10 マトリクス。ステップが cv2.imread を直接呼ばない)
8. **[PIT-CV2-XY-002] 吹き出しがコマ境界をまたぐと X-Y カットが分割できない** — ガターが狭いのではなく、境界の余白がセリフの吹き出しで塞がれて連続ガターが消えるため、隣接コマが 1 枚に統合される。`MIN_GUTTER_PX` を下げても直らない。→ 検索用途では**許容**(統合コマでも該当テキストを含むのでヒットする。やや大きめの画像が出るだけ)。過分割で吹き出しを割る方が OCR には有害。精度が要るなら吹き出しマスク後に再カット等を検討(将来拡張=EXCL-02)。
   確認環境: win 実走(2026-06-28)/ 回帰: —(許容と明記。過分割にしない)

## 10. 完成判定(買い手の AI が自己検証)
