# レシピの型(章立て規約)

在庫レシピ `recipes/**/{name}.md`(公式は `official/{カテゴリ}/` 配下、置き場は再帰で読まれる)は次の章立てで書く。**章番号は固定**(builder.md /
recipe-test.sh がこの番号を参照するため、勝手に振り直さない)。各章は「ここに何を書くか/
何を書かないか」が決まっている — 同じことを複数の章で別々に定義しない(矛盾の元)。

冒頭は notion-wp.md と同じ HTML コメント枠(由来 / 状態 / ★固有値を焼かない宣言)。

---

## レシピ先頭メタ(★配布ゲート)— 検証ステータス + 動作確認 + 配布元検証

HTML コメント枠の直後の本文メタ(用途分類 / 必要ビルダー VERSION の並び)に、**3 行**入れる。
**検証ステータス**(実ビルドで裏取りできているか=配布の関所)に加え、**動作確認**(どの OS で実機緑が取れたか)と
**配布元検証**(配布元=作者が最終サインオフしたか)。この 3 つは**直交する別軸**で、互いに意味を再定義しない。

```md
- 検証ステータス: `verified` — skeleton(骨組みのみ・未実装)/ experimental(実装したが未実証)/ verified(実ビルドで結晶化済み)。**verified だけが配布対象**
- 動作確認: `mac ✅` / `win ⬜` — 実機で建てて緑を取れた OS(✅=検証済 / ⬜=未検証=動かない確証ではない / ➖=非対応)
- 配布元検証: `✅` — 配布元(作者)が実機で最終サインオフ(⬜=未。量産物が AI 判定で verified でも本人未確認を区別)
```

| 値 | 意味 | 配布(PRO_RECIPES) |
|---|---|---|
| `skeleton` | §1 機能構成表 + §3 魔法のタネ仮説だけ。§5/§6 が空 or 推測 | **不可**(待ち行列。実ビルドで昇格させてから) |
| `experimental` | 一通り書いたが実機で建てて検証していない | **不可**(踏む地雷が未収集=買い手を誤誘導しうる) |
| `verified` | required + optional-enabled を実ビルドで建て、§5/§6 が当事者文脈から結晶化済み | **可** |

- **昇格は実ビルドだけが行う**。テンプレ・一般知識から書いただけでは `verified` にしない(§5 建てる順番 /
  §6 地雷の症状→直し方は、建てて初めて手に入るプロセス知。型 lint は構造しか見ない=中身の真偽は保証しない)。
- 配布ゲートは機械で固定: `scripts/build-dist.sh` が **PRO_RECIPES のレシピに `verified` 以外を見つけたら同梱を止める**
  (default-deny の延長)。`scripts/recipe-lint.sh` は値が 3 語彙かを検査する。

### 動作確認(mac / win)と配布元検証 — 3 軸の使い分け

| 軸 | 問い | 値 | 配布ゲート |
|---|---|---|---|
| `検証ステータス` | §5/§6 が実ビルドで結晶化されたか(構造の裏取り) | skeleton / experimental / verified | **ゲート**(verified 以外は配布不可) |
| `動作確認` | **どの OS で実機緑が取れたか** | `mac`/`win` それぞれ ✅(検証済) / ⬜(未検証) / ➖(非対応) | **非ゲート**(win ⬜ でも配布できる。下記) |
| `配布元検証` | 配布元(作者)本人の最終サインオフ | ✅ / ⬜ | 非ゲート(信頼の目印) |

- **win ⬜(未検証)でも配布してよい**。配布をブロックしない=「Win は未検証だが配りたい」を許す。代わりに**買い手が一覧で ⬜ を把握したうえで使う**:
  - レシピ一覧テーブルに `Mac` / `Win` / `検証` 列を出す(builder.md「レシピ一覧テーブル」)。
  - **win ⬜ のレシピを Windows 上で「これ作って」した時だけ**、ビルダーが「このレシピは Win 未検証です。続けますか?」と 1 回確認(柱1=事故らない)。
  - build-dist は配布時に「Win 未検証で配布するレシピ: …」を**表示のみ**(止めない=了承して配る運用)。
- **⬜ は「動かない確証」ではない**(まだ実機で建てて緑を取っていない、の意)。実機検証で緑が取れたら ✅ に上げる。`➖` はそのスタックが当該 OS 非対応(例: 特定の Linux 専用バックエンド)。

## レシピの形(2種)— 単体レシピ / 核+アダプタ

レシピは「質を保ったまま増やす」ために 2 つの形を持てる。**新しい派生は、別レシピを 1 本増やすより
まず「アダプタを足せないか」を先に考える**(検証済みの核を再利用でき、量産の本命)。

| 形 | いつ | §1 表の ID 接頭辞 | 例 |
|---|---|---|---|
| **単体** | 1 プロダクトを丸ごと再現 | `CORE-` / `FEAT-` / `EXCL-` | `notion-wp` |
| **核+アダプタ** | 普遍核に「種別」を差し替えて家族化 | 上記 + `ADAPT-`(アダプタ単位) | `xserver-site-ops`(核+WP/静的HTML) |

**核+アダプタの規約**(worked example: `recipes/official/utils/xserver-site-ops.md`):

- **CORE-**\* = サイト種別/派生に依存しない普遍核。これが家族の検証資産。
- **ADAPT-**\* = 核の上に載る種別アダプタ。§1 表では各アダプタを 1 行の機能(`optional-enabled` か
  `optional-disabled`)として持つ。**新派生 = アダプタ行を 1 つ足す**(レシピを増やさない)。
- **未検証アダプタは必ず `optional-disabled` + 行に「未検証」明記**にする。既定 OFF=SKIP なので、レシピ全体の
  `検証ステータス: verified`(核 + 既定 ON 機能が実ビルド済み)と両立する。実ビルドで裏が取れたら
  `optional-enabled` に昇格。
- ID 語彙に `ADAPT-` を足す以外、§1〜§10 の型・状態語彙(4 つ)・3 値判定はそのまま。

## 章ごとの役割(★各機能の状態を決めるのは §1 の機能構成表「だけ」)

| 章 | 役割 | 書く | 書かない |
|---|---|---|---|
| §1 これは何 / 機能構成 + 完成形 | **機能構成表が正本**。必須/任意/不採用を一元決定 | 機能構成表 + 受け入れ基準(表参照型) | 個々の機能を「入れる/入れない」と二重定義しない |
| §2 スタック | 採用技術と一行理由 | 層×採用×備考の表(構築手順は `knowledge/{stack}.md` を参照) | Phase の手順・構築手順のベタ書き |
| §3 魔法のタネ ★変えるな | 崩すと別物になる本質(スタック非依存) | 再現必須の原理 | 可変の見た目・knob |
| §4 改変の余地 ★変えていい | knob を **3 分類**(下記)で提示 | 軽量設定 / 機能モジュール / 派生アーキ | 「必須かどうか」(それは §1 表) |
| §5 再現の順路(Phase + 検証) | 作る順番だけ | 各 Phase の「作る/検証(緑条件)」。任意 Phase は機能 ID と状態を明記。**Phase 0 土台(環境構築)は `knowledge/{stack}.md` を参照**(手順をベタ書きしない) | 完成可否の最終判定(それは §10)・構築手順の重複展開 |
| §6 固有の地雷 + 直し方 | 失敗症状と直し方だけ | **PIT ID** + 症状 → 原因 → 直し方(なぜ効くか)+ 確認環境 / 回帰(下記規約) | スタック共通地雷(`knowledge/{stack}.md` へ集約=環境構築コンポーネント) |
| §7 固有スキル / 道具 | 標準テンプレに無い同梱物 | スキル名と役割 | 実装全文(@pro-only で) |
| §8 ハーネス宣言 | templates/ から焼く宣言 | 用途の標準一式 + 固有上書き | ハーネス本体 |
| §9 適応指示 | 環境差・安全側・固有値剥離 | 安全側デフォルト / 固有値の置換表 | 実値(プレースホルダのみ) |
| §10 完成判定 | 合否判定だけ | **機能構成表に対する 3 値判定**(下記)+ **テストマトリクス**(下記) | 機能の有無の再定義 |

## §1 の機能構成表(SSOT)— これがこの型の心臓

§1 の冒頭に必ず置く。**この表だけが各機能の状態を決める**。以降の章は状態を再定義せず
この表を参照する(「Notion 移行を実装する」ではなく「FEAT-05 が enabled の時だけ実装する」)。

```md
## 1. これは何 / 機能構成 + 完成形(受け入れ基準)

### 機能構成(★ここだけが必須/任意/不採用を決める正本)

| ID | 機能 | 状態 | Phase | 完成判定 |
|---|---|---|---|---|
| CORE-01 | （崩すと別物になる本質） | required | Phase 2 | PASS 必須 |
| FEAT-01 | （既定で入れる任意機能） | optional-enabled | Phase 6 | enabled なら PASS 必須 |
| FEAT-02 | （既定で入れない任意機能） | optional-disabled | Phase 7 | 既定 SKIP |
| EXCL-01 | （このレシピに混ぜない） | excluded | — | 別レシピ |

### 完成形(受け入れ基準)
- [ ] required の機能がすべて緑
- [ ] enabled な optional がすべて緑(disabled は SKIP=欠落ではない)
- [ ] ローカルで上が動く ← ここまでが「完成」。公開は §9 の合図から
```

### 状態語彙(この 4 つだけ)

| 状態 | 意味 | 完成判定での扱い |
|---|---|---|
| `required` | 無いと別物(魔法のタネ含む) | **必ず PASS**。FAIL なら配布不可 |
| `optional-enabled` | 既定 ON。買い手が外せる | enabled の間は PASS 必須 / disabled にしたら SKIP |
| `optional-disabled` | 既定 OFF | 既定は **SKIP**(欠けていても正常)。ON にしたら PASS 必須 |
| `excluded` | このレシピには含めない | Phase にもテストにも出さない(別レシピへ) |

## §4 の knob 3 分類(誤解事故の防止)

「変えていい」を粒度で 3 つに割る。**WordPress→Next.js のような派生をユーザー(や AI)が
『少し変えるだけ』と誤認する事故**を構造で防ぐ。

| 分類 | 中身 | 変えると |
|---|---|---|
| **軽量設定** | 配色 / フォント / カラム数 / ダーク・ライト / ポート | 設計を変えずに差し替え可。サイレント適用してよい唯一の層 |
| **機能モジュール** | §1 表の optional-* 機能(front 編集 / 移行 等) | Phase とテストが増減。§1 表の状態で ON/OFF |
| **派生アーキ** | 母体スタックの差し替え(WP↔Headless 等) | **knob ではない**。魔法のタネ(§3)だけ移植して別実装=実質「別レシピ」。提案 → ユーザー GO |

## §10 の完成判定(3 値:PASS / FAIL / SKIP)

§1 の機能構成表を基準に判定する。「§1 を全部緑」とは書かない(任意機能を OFF にすると
構造的に満たせなくなるため)。

```md
## 10. 完成判定(買い手の AI が自己検証)
§1 機能構成表に対し:
- required = すべて PASS(1 つでも FAIL なら未完成)
- optional-enabled = enabled のものは PASS / disabled にしたものは SKIP
- optional-disabled = 既定 SKIP(ON にしたなら PASS)
かつ `scripts/validate-output.sh` が PASS、§5 各 Phase の検証が緑。
```

## §6 の地雷 ID(PIT)規約 — 固定 ID + 確認環境 + 回帰(2026-07-06 新設)

各地雷エントリの太字見出しに固定 ID を付け、末尾に確認環境と回帰を 1 行添える。

- **ID 形式**: `PIT-{ドメイン}-{連番3桁}`(例 `PIT-WP-REST-001`)。ドメインは**技術領域タグ**(`WP-REST` / `ALPINE` / `PNPM` / `XSRV-PATH` / `CV2-IO` 等)であって**レシピ名ではない**
- **レシピに紐づけない理由**: 同じ地雷が別レシピで再発した時に**同じ ID で参照**できる(横展開)。同一 PIT が 2 レシピ以上に現れたら `knowledge/{stack}.md` への昇格を検討(rule of two)
- **採番**: 新しい ID は `grep -rn 'PIT-{ドメイン}-' recipes/ recipes-candidates/ knowledge/` して最大番号 +1(欠番は再利用しない)
- **書式**(既存の 症状→原因→直し方 の後ろに 1 行足すだけ):

  ```md
  2. **[PIT-WP-REST-001] プレーンパーマリンクで `/wp-json/` が死ぬ**
     (症状 → 原因 → 直し方 は従来どおり)
     確認環境: mac wp-env(2026-06)/ 回帰: TEST-002
  ```

- **回帰**: 機械で取れるものは §10 テストマトリクスの TEST 行にして ID で相互参照。取れないものは `回帰: 手動(何を見るか)`

## §10 のテストマトリクス — 「レシピに書いた完成条件」=「スクリプトが確認する完成条件」(2026-07-06 新設)

§10 の 3 値判定の下に機械可読のテスト表を置く。`scripts/recipe-test.sh` が **auto 行を実際に実行**する(表駆動 healthcheck)。

```md
| TEST ID | 対象 | 種別 | tier | 検証方法 | 期待値 |
|---|---|---|---|---|---|
| TEST-001 | — | auto | smoke | `curl -fsS -o /dev/null "http://localhost:${WP_PORT:-8888}/"` | トップ 200 |
| TEST-003 | PIT-WP-REST-002 | auto | full | `curl -fsS -o /dev/null "http://localhost:${WP_PORT:-8888}/?rest_route=/wp/v2/posts&orderby=menu_order&order=asc"` | 400 でなく 200 |
| TEST-006 | CORE-03 | manual | full | ドラッグ → リロード | 順序維持 |
```

- **TEST ID**: `TEST-{3桁}`。レシピ内で一意
- **対象**: §1 機能構成表の機能 ID / §6 の PIT ID(=回帰テスト)/ `—`(土台など表に無いもの)
- **種別**: `auto`(recipe-test.sh が実行)/ `manual`(人・AI が §5/§10 の手順で確認)
- **tier**: `smoke`(生成テストで常に実行)/ `full`(`--tier full` の時だけ)
- **検証方法**(auto 行): バッククォートで **1 本のシェルコマンド**。cwd=生成プロジェクト直下で実行され **exit 0 = PASS**。
  **パイプ `|` を書かない**(md 表が壊れる)— 複雑な検証は生成物側にスクリプトを置いてその実行を書く。
  `WP_PORT` は driver が生成物の `.wp-env.json` から注入する(無ければ空=既定値が効く)
- **required 機能は最低 1 行の TEST でカバー**する(auto でも manual でもよい。lint が WARN で見張る)

## 結晶化(②)の最後に Recipe Lint を通す

型は作るだけでは AI がそのうち崩す。結晶化の最後に `scripts/recipe-lint.sh <レシピのパス>`(在庫なら `recipes/official/{カテゴリ}/{name}.md`)
を実行し、**ERROR が 1 件でもあれば配布(PRO_RECIPES 登録)しない**。WARN は人間が確認。
詳細は [scripts/recipe-lint.sh](../../scripts/recipe-lint.sh) 冒頭。
