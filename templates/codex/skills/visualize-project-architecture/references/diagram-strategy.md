# 図解の設計基準

## 1. 最初に決めること

レイアウトより先に次を決める。

1. 読者は誰か
2. 読者が画像を見た後に説明できるようになる一文は何か
3. 情報同士の中心的な関係は何か
4. どこから見始め、どこで理解が完了するか

「機能を全部載せる」ではなく、「対象の仕組みを誤解なく説明できる」を完成条件にする。

## 2. 関係から図法を選ぶ

| 情報の中心 | 第一候補 | 適する内容 |
|---|---|---|
| 順番 | プロセスフロー / スイムレーン | 操作手順、申請、公開、送信、受け取り |
| 層と担当範囲 | レイヤー図 | 画面、処理、保存、外部サービス、ローカル処理 |
| 接続と依存 | トポロジー / 関係図 | サーバー、API、サービス間連携、組織間の担当 |
| データの移動 | データフロー図 | 入力、変換、保存、取得、配信 |
| 時間と状態 | ライフサイクル / 状態図 | 作成、公開、期限、停止、削除、失敗時の復帰 |
| 違い | 比較図 / Before-After | 現行と移行後、複数案、利用者別の違い |
| 全体と内訳 | 階層図 / マップ | プロジェクト内容、機能群、要件、フォルダの役割 |
| 画面中心の理解 | UI中心図 + 周辺フロー | 操作画面が価値の中心で、裏側の処理を補足したい時 |

必要なら2〜3種類を組み合わせる。例えば「レイヤー図の中へデータフローを重ね、右端に例外処理を置く」。すべてを横一列の工程表へ変換しない。

## 3. 非エンジニア向けの翻訳

- 技術名を消さず、役割を同じ場所に添える。
  - `Cloudflare Worker — URLを受け取り、表示内容を返す処理`
  - `R2 — 公開するファイル本体の保存先`
- 最初に利用者の行動を書く。「HTTPリクエスト」ではなく「共有URLを開く」から始める。
- 箱の見出しは名詞だけでなく動作を含める。「Worker」より「Workerが一覧を組み立てる」。
- 専門用語の説明を離れた用語集だけに置かない。最初に現れる場所で短く説明する。
- 数値は判断に必要なものだけを載せ、意味も添える。
- 未確認事項は疑問符、破線、注記など、確定事項と異なる表現にする。成立条件や未検証表示を下端だけへ置かず、該当する主張の近くに同じ可読性で示す。

## 4. 矢印を事実監査する

図を描く前に、根拠表へ次の形で全矢印を書く。

| 操作 | 起点 | 終点 | 動くもの | 根拠 |
|---|---|---|---|---|
| 例: 一覧を開く | 閲覧者 | Access | HTTPSリクエスト | 設定・ルート |
| 例: 認証後に処理 | Access | Worker | 許可済みリクエスト | 実装・構成 |

- 公開時と閲覧時、書き込みと読み出し、通常処理と削除を別の行にする。
- 物語の順番を優先して、実際の通信方向や担当を反転させない。
- 箱同士の近さだけで接続を暗示しない。双方向なら往路と復路、または双方向である理由を示す。
- URL、ID、一覧などを「作る」主体と、それを「受け取って返す」主体を区別する。

## 5. 構成の作り方

- 一番大きな面積を、読者が理解すべき中心フローまたは中心関係へ使う。
- 補足、例外、安全上の注意は中心より弱い階層へ置く。ただし重要な分岐は矢印上で示す。
- 同じ意味のものを近くへまとめ、異なる担当・環境・状態は余白、背景色、境界線で分ける。
- 実画面が価値を説明する場合は、飾りではなく処理の入口または結果として配置する。
- 実画面の再現は、読めないサイズで忠実に写さず、理解に必要な行・ボタンだけへ簡略化する。
- 色は「担当」「環境」「状態」「線の意味」のいずれか1つを主目的にする。装飾だけで色数を増やさない。
- 実ロゴがローカルに無ければ、外部から無断取得せず、サービス名と簡潔な汎用アイコンで示す。

## 6. 固定テンプレート化を防ぐ

- ヘッダー、左側フロー、右側要点、下部用語集という固定構成を前提にしない。
- `フロー4本`、`要点6件`など、情報を入れるための固定個数を作らない。
- 前回のHTMLをコピーする場合は、情報の関係が同型である理由を計画へ書く。理由がなければ新しく構成する。
- 文章が収まらない時は、文字縮小や情報削除より先に、箱の統合、図法変更、詳細図への分離を検討する。
- 見た目の変化だけを目的に図法を変えない。意味が同じなら同じ図法でもよい。

## 7. 4K正本と1080p共有時の基準

- キャンバス: 3840×2160、16:9
- 安全余白: 四辺80px以上
- タイトル: 56〜76px程度
- 大見出し: 34〜48px程度
- 通常本文: 32〜36px以上
- 補足・バッジ・凡例: 28px以上。例外なく28px未満を使わない
- 主要フロー: 3〜7段階を目安にする。分岐が多い場合は縦横を組み合わせる
- 線: 背景とのコントラストを確保し、矢印先端を明瞭にする

4K正本は共有時に1920×1080へ縮小される前提で作る。確認用画像を実際に開き、補足まで読めなければ情報を減らすか詳細図へ分ける。文字を小さくして固定枠へ合わせない。
