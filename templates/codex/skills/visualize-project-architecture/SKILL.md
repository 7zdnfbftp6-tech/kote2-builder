# 複雑なプロジェクトを図解する

実装や資料を根拠に、「誰が、何をすると、どこで何が起き、何が返るか」を対象読者が追える図解へ変換する。技術名を消さず、同じ枠内に役割を平易に添える。色や書体は一貫させても、本文レイアウトは情報の関係に合わせて毎回設計する。

## 成果物

プロジェクトルートの `visuals/` に次を作る。

- `project-overview-evidence.md`: 図に載せた事実と根拠
- `project-overview-plan.md`: 読者、伝える結論、採用した図法、パネル構成
- `project-overview.html`: 図解の編集可能な正本
- `project-overview.png`: 3840×2160の共有用画像

1枚で誤解なく説明できない場合は、概要を `project-overview.*` に保ち、`detail-{topic}.html` / `.png` を必要最小限だけ追加する。情報を削って1枚へ押し込まない。

## 手順

### 1. 調査する

1. 現在の作業ディレクトリから対象を確定する。対象読者が未指定なら非エンジニアを既定にする。
2. `AGENTS.md`、`CLAUDE.md`、README、マニフェスト、設定、画面、入口処理、保存処理、外部連携を必要な範囲だけ読む。
3. 利用者の操作、処理の順序、保存先、外部サービス、公開範囲、例外・終了条件を実装から追う。
4. `.env`、認証JSON、鍵、トークン、個人プロフィールを読まない。長いパス、秘密値、公開不要の識別子を図へ載せない。
5. `project-overview-evidence.md` に「図の説明 / 確認した事実 / 根拠ファイル」を記録する。推測は事実と分ける。
6. 図に描く矢印ごとに「起点 / 終点 / 動くもの / 根拠」を表にする。公開、閲覧、保存、削除など目的の異なる流れを1本の物語へ混ぜない。

### 2. 説明の設計を先に作る

`references/diagram-strategy.md` を必ず読み、情報の関係から図法を選ぶ。

`project-overview-plan.md` に次を書く。

- 読者と、画像を見た後に理解してほしい一文
- 主役となる利用者または処理
- 採用する図法と、その図法が内容に合う理由
- パネル構成、主要な箱、矢印の意味
- 実画面、アイコン、凡例を使うか
- 3840×2160を50%表示した時にも残す情報と、省く詳細
- 概要から外す情報と、必要なら詳細図へ移す理由

前回の図や同梱例のレイアウトを既定にしない。内容が同じ関係を持つ場合だけ再利用する。

### 3. 図解HTMLを作る

`project-overview.html` を案件ごとに設計する。固定のカード数、サイドバー、用語集、フロー本数を前提にしない。

- 3840×2160の16:9キャンバスを使い、本文は画面端から十分離す。
- HTML / CSS / SVGで、文字を選択できる状態を保つ。外部CDNやネットワークを必須にしない。
- CSSの文字サイズは検査可能なpxで明示する。最小28px、通常本文32〜36pxを下限とし、小さくしないと入らない情報は省略または詳細図へ移す。
- 矢印の向き、線種、色に意味を持たせ、凡例と食い違わせない。
- 技術名には「Cloudflare R2 — 共有ファイルを保存」のように役割を併記する。
- 画面が理解の中心なら、確認済みの実画面または簡潔なUI再現を主要パネルに使う。
- 比喩やキャラクターで実体を置き換えない。宣伝文句、未確認の性能値、存在しないAI処理を加えない。
- 未確認、設定後のみ成立、追加条件が必要な事実は、主張と同じ箱または直下へ明示する。下端の小さな注記だけで条件を補わない。
- 装飾より、視線の順番、まとまり、因果関係、主従を優先する。

### 4. PNGへ変換する

Node.js 18以上で実行する。

```bash
node .agents/skills/visualize-project-architecture/scripts/render-visual.mjs \
  --html visuals/project-overview.html \
  --png visuals/project-overview.png \
  --preview visuals/project-overview-preview.png
```

スクリプトは28px未満の文字を拒否し、Chrome、Edge、Chromiumのいずれかで4K正本と1920×1080確認用画像を撮影する。追加パッケージとネットワーク接続は不要。自動検出できない場合は `--browser "{実行ファイルのパス}"` を付ける。

### 5. 意味と見た目を確認する

4K PNGと確認用PNGを画像表示ツールで実際に開き、最低限次を確認する。

- 3840×2160で、文字切れ、重なり、画面外へのはみ出しがない
- 最初の10秒で「何の図で、何ができるか」が分かる
- 1920×1080の確認用画像で、主要説明だけでなく残した補足も読める
- 利用者の操作から結果まで視線で追える
- すべての矢印が根拠表の「起点 / 終点 / 動くもの」と一致する
- 対象読者に必要な用語説明が、その用語の近くにある
- 実装にない機能、根拠のない安全性、秘密値、個人情報がない
- 内容の異なる対象を、同じ定型レイアウトへ無理に合わせていない

問題があれば文字を小さくする前に、構成、グルーピング、図法を見直す。重要情報が収まらなければ詳細図へ分ける。最大2回は画像を見て修正する。合格後は確認用の `project-overview-preview.png` を削除し、4つの正本だけを残す。

### 6. 報告する

PNG、HTML、根拠表の順に案内する。採用した図法と「この図で分かること」を短く説明し、未確認事項があれば1〜3点に絞って明示する。
