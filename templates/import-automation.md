# 自動化プロジェクト登録プロトコル(取り込み = 台帳登録)

別途生成した自動化プロジェクトを、この AI 秘書から使えるようにする時の手順。
**実体はコピーしない。** 秘書ルートの台帳 `automations.md` に「場所と呼び出し方」を登録するだけ。実行時は元の場所を直接呼ぶ。

- なぜコピーしないか: コピーは元プロジェクトの更新から取り残されてズレる・`.env`(秘密)まで複製される。秘書に必要なのは「何がどこにあって、どう呼ぶか」のリストだけ。

## 起動キーワード

ユーザーが以下のような言い回しをしたら、このプロトコルを実行する:

- 「○○を取り込んで」
- 「○○を秘書に組み込んで」「○○を登録して」
- 「○○を秘書から呼べるようにして」
- 「前に作った○○を使えるようにして」
- 「`/import-automation`」(スラッシュコマンドとして直接呼ばれた場合)

## 登録対象の判定(最初に確認する)

登録できるのは **葉っぱの自動化(単機能のスキル / スクリプト)** だけ。**人格を持つ「秘書」そのものは登録しない**。秘書から秘書を呼ぶと人格が二重になり、どのフレームが本体か分からなくなる。

**中身を理解しようとせず、構造で機械的に判定する**:

| 登録対象が… | 判定 | 扱い |
|---|---|---|
| 自前の台帳(`automations.md`)や取り込み済み `automations/` を持つ | **秘書(ルーター)** | そのまま登録しない |
| CLAUDE.md が「あなたは〇〇さんの AI 秘書です」+「できること」リストの索引型 | **秘書(ルーター)** | そのまま登録しない |
| 台帳を持たず、SKILL.md / `run.*` / スクリプトなど単機能が中心 | **葉っぱの自動化** | 登録してよい |

「秘書(ルーター)」と判定したら**自動で進めず**、必ずユーザーに確認する:

> これは自動化単体ではなく「秘書」のようです。秘書ごと登録すると人格が二重になります。中の {葉っぱの名前} だけを登録するのが安全ですが、どうしますか?

## 手順

### 1. 元プロジェクトのパスを特定

ユーザーが言ったプロジェクト名(例: `news-mailer`)から、元の場所を推定:

- まず `../{name}/`(秘書本体と同じ階層 = ビルダーの output/ 配下)を探す
- 次に `output/{name}/`、`../output/{name}/` を探す
- ユーザーが絶対パスで言ったら最優先

見つからない・複数候補ある場合は**1 問だけ確認**:「`どこにありますか? 例えば ../news-mailer ですか?`」

### 2. 登録内容を確認

元プロジェクトを Read / Glob で軽くスキャンして、以下を把握する(**コピーしないので中身は読むだけ**):

- プロジェクトの一行サマリ(SKILL.md / README.md 冒頭から取れる範囲で)
- 起動方法(README.md / `package.json` の scripts / `run.py` 等から推測)
- 依存セットアップの有無(`package.json` / `requirements.txt` / `.env.example`)

### 3. 登録内容を提示して OK を取る

「動作原則(変えない)」の設計確認ゲートに従い、いきなり書き込まない。以下の形で提示:

```
台帳への登録内容:

## {name}
- 場所: {source-path}(実体はここのまま。コピーしません)
- できること: {1 行サマリ}
- 呼び出し方: `cd {source-path} && {起動コマンド}`
- 目標・頻度(任意): {ユーザーが目標を口にしていれば。無ければ空欄}

CLAUDE.md「できること」リストに追記する 1 行:
- ✨ {機能名} — 台帳 `automations.md` 参照
  {1 行サマリ}

呼び出しキーワード:
「{ユーザーが使いそうな呼び出し方、例: 「ニュースメール送って」}」

これで登録して OK ですか?
```

### 4. OK が出たら実行

順番:

1. **台帳に追記**: `automations.md` にエントリを 1 つ追加(無ければ台帳ファイルを作る)
2. **CLAUDE.md 更新**: 「できること」リストに**1 行だけ追加**。全体を書き換えない
3. **疎通の軽い確認**: 登録した場所が実在するか(`ls {source-path}`)だけ確かめる。実行はしない
4. **元プロジェクトには一切触れない**: コピーも移動も編集もしない。`.env` / `aboutme.md` / `ai-behavior.md` / `domain-knowledge.md` はすべて元の場所に置いたまま(各自動化はこれらで自分の専門を保っている)

### 5. 完了報告

```
登録完了!

✨ できること: {機能名}

これからは「{呼び出しキーワード}」と話しかけると、{機能名} が動きます。
実体は {source-path} にあり、そちらを直接呼びます(この秘書へのコピーはありません)。
元プロジェクトを更新すれば、秘書からの呼び出しにもそのまま反映されます。
```

## 禁止事項

- ❌ **元プロジェクトをコピー・移動・削除・編集する**(登録は台帳への追記だけ)
- ❌ **CLAUDE.md 全体を書き換える**(できることリストに 1 行追加するだけ)
- ❌ **`.env` を秘書側に持ち込む・マージする**(秘密は元の場所から動かさない)
- ❌ **ユーザーの OK を取らずに台帳へ書き込む**(設計確認ゲートを飛ばさない)
- ❌ **同名エントリを無断で上書きする**(必ず確認する)
- ❌ **依存インストール(`pnpm install` 等)を勝手に走らせる**(必要ならコマンド提示まで)
- ❌ **人格を持つ「秘書」を、確認せずそのまま登録する**(「登録対象の判定」を飛ばさない)

## 同名エントリがある時の挙動

台帳に `{name}` が既にある時は、場所を見比べて**1 問だけ確認**:

> 台帳に同じ名前の登録があります(場所: {既存の場所})。今回の {新しい場所} で**上書き**しますか、それとも **{name}-2** など別名で登録しますか?

## 旧方式(コピー式)からの移行

この秘書に `automations/{name}/`(コピー式の取り込み)が残っている場合、ユーザーが望めば移行できる:

1. コピー元(元プロジェクト)がまだ存在するか確認する
2. 存在すれば「元プロジェクトを台帳に登録し、コピー(`automations/{name}/`)は削除できます」と提案。**削除は必ずユーザーの OK を取ってから**(コピー側にだけ入った修正が無いか、先に差分も見せる)
3. 元プロジェクトが見つからない場合は、コピーの方が唯一の実体。**消さずに**そのコピー自体の場所を台帳に登録する

## 想定ユースケース

- **講座の物語**: 受講者が前の章で作った自動化を、AI 秘書の章で登録して「秘書が能力を獲得する」体験
- **個人運用の成長**: 単独で動いていた自動化を、徐々に秘書経由で呼べるようにまとめる
- **目標運転**: 台帳に目標・頻度を書くと、秘書が「目標に対して今どこ・今日どれを回すか」を提案できるようになる

いずれも「**元プロジェクトを壊さず、秘書に能力を増やしていく**」が共通の体験。
