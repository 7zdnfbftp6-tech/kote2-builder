# 定時実行(ルーチン / cron / scheduled jobs)のルール

**参照タイミング**: 「毎朝」「毎日」「定期的に」のような **定時実行を実装・設計する作業** に入る時だけ読む。ユーザーが定時実行の話を出していない普通の依頼では参照しない(関係ない判定や言及を会話に出さない)。

---

## 実行手段の選択

定時実行が **明示的に要件にある場合のみ**、以下の順で検討する:

1. **Claude Code のルーチン**(`/schedule`)— Claude Code ネイティブのスケジューラ。MCP / スキルがそのまま使える
2. **外部 cron / GAS / n8n** — ルーチンでは不可能 or 不向き(下記参照)が判明してから

ルーチンで **不可能 or 不向き** なケースの例:

- ローカル PC のハードウェア情報を読む(電池残量、デバイス状態、ローカルアプリ操作 等) → ローカル `launchd` / `cron`
- ローカル LAN 内のサービスにしか接続できない → ローカル実行手段
- 既に運用中の n8n / GAS スタックに統合する方が筋がいい場合

## env(秘密情報)の二重化

ルーチンで動かす場合、**ローカルの `.env` は読まれない**。必要な秘密情報はルーチン作成時に Cloud Environment の env として **別途登録** する。

- キー名は `.env.example` と揃える(ローカル開発との対応関係を明確にするため)
- README にローカル開発用 (.env) と本番用 (Cloud Env) の二重化手順を書く

## 最小権限

ルーチンに与える権限は **そのジョブが触る最小集合だけ** に絞る:

- MCP コネクタ: 必要なサーバーだけ allow
- ネットワーク接続先ホスト: 必要なドメインだけ allow(**リダイレクト先ホストも別物として列挙**)
- Bash 系: deny だけでなく allow も最小限に設計

## 冪等性ガード(メール・通知・課金 API 必須)

スケジューラが何らかの理由で 1 回の起動で複数回叩いた場合に、**重複送信を物理的に不可能にする**ガードをジョブ側にも実装する。プロンプトの注意書きだけに頼らない:

- 送信履歴ファイル(日付キー等)で同日 2 回目を弾く
- 初回テストは `dry-run` フラグで本送信させない
- リダイレクト(302 等)やリトライ可能エラーを「失敗」扱いしない curl オプション固定(例: `--max-redirs 0` + 302 を成功扱い)
- ルーチンプロンプト本体(SKILL.md / `.claude/schedules/*.md` 等)に **「送信は 1 回のみ。失敗してもリトライしない。重複より欠損を選ぶ」** を明示

## 検討プロセスの広報禁止

ユーザーが定時実行を話題にしていない依頼に対して、「ルーチンでは作れません」のような **不採用判定を会話に出さない**。実装手段の選択は内部で済ませて、結果(launchd 案件です、等)だけ簡潔に伝える。
