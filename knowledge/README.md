# knowledge/ — 環境構築コンポーネント(スタック別の構築手順 + 地雷)

このフォルダは、ビルダーやレシピが**条件に該当した時だけ読む**「非自明なスタック別のコツ」です。`{stack}.md` が 1 ファイル = 1 スタック/ツール(pnpm / Cloudflare / n8n / wp-env 等)。pnpm の `allowBuilds` 地雷のように、**Claude が確実には出さない / 複数のレシピが共有する**技術知識だけを置く(「pnpm とは」式の一般解説は置かない=Claude が代替する)。

> **このフォルダ = 環境構築コンポーネント層(2026-06-24 正式化)**。各 `{stack}.md` は「**セットアップ(構築手順)+ 地雷/予防**」の両方を持つ再利用部品。レシピ家族をまたいで共有する(同じ n8n 構築を automation レシピと AI 秘書レシピが共有)。**核+アダプタ(=1 レシピ家族内の差し替え)とは直交する軸**で、環境構築は横断層のここに置く。狙いは「**n8n の構築を直すのは `knowledge/n8n.md` 1 箇所**=陳腐化最小」。詳細は下の §「環境構築コンポーネントとして使う」。

> **役割分離(2026-06-17)**: 以前はここに用途別仕様(`usecase-*`)と在庫レシピ(`recipe-*`)も同居していたが、1フォルダ1役割に分けた。**「事前に織り込む指南書(レシピ)」と「事後に引く資料(ここ)」は別物**:
> - **`recipes/`** — 表の成果物。「目的物を仕上げる指南書」(完成形 + 再現の順路 + 地雷)。**事前に**織り込む。配布は許可リスト方式(verified のみ。Free=`FREE_RECIPES` 1本 / Pro=`PRO_RECIPES` カタログ)
> - **`usecase/`** — ビルダーの用途別生成仕様(自動化 / AI 秘書 / Web)。用途分類が決まったら該当ファイルだけ読む
> - **`knowledge/`(ここ)** — レシピやビルダーが**裏で引く**共通のコツ。スタックが決まったら該当ファイルだけ読む

## builder.md との役割分担

| ファイル | 役割 |
|---|---|
| `builder.md` | ビルダーのコア仕様(ヒアリング・設計確認・非エンジニア向け説明・リビジョン・自己修復・**用途判定とルーティング**)。**常時参照する最小限**。 |
| `recipes/**/{name}.md`(別フォルダ・再帰。公式は `official/{カテゴリ}/`) | 在庫レシピ=「目的物を丸ごと再現する指南書」。用途判定の前にマッチを見る。配布は許可リスト方式(FREE/PRO_RECIPES)。 |
| `usecase/{name}.md`(別フォルダ) | 用途分類ごとの生成仕様(スタックデフォルト・初期構造・その用途特有の要件)。**該当用途の生成時だけ読む**。 |
| `aboutme.md` §3 / `ai-behavior.md` | どのツールを使うか(pnpm / Astro / Tailwind 等)の **好み・選択**。デフォルトを上書きする。 |
| `knowledge/{stack}.md`(ここ) | 選んだスタック特有の **「使うなら誰でも踏む」技術的ノウハウ**。好みでも道具非依存でもない、中間の知識。 |

## 4つの仕組みの関係(全体像)

ビルダーが生成するプロジェクトには「失敗から学ぶループ」が組み込まれている。`knowledge/` はそのループの **最上流(予防)** に位置する:

```
knowledge/{stack}.md  …【予防/上流】次に生成する時、最初から守る ← ビルダー本体が生成時に読む
        ↓ (生成時に参照)
  [プロジェクト生成]
        ↓
  .claude/hooks/ 3本   …【検知】Bash 失敗を拾い、セッション終了時に対処を強制
        ↓
  self-heal.md         …【手順】特定→修正→確認→記録 の5ステップ
        ↓
  ## ハマりどころ       …【保管/下流】そのプロジェクト固有の技術ハマり
        ↓ (昇格)
  スタック共通と判明したものを knowledge/ へ引き上げる ──┘
```

- **hooks / self-heal / ハマりどころ** は **生成されたプロジェクトの中**で完結する3点リレー(検知 → 手順 → 保管)
- **`knowledge/` だけはビルダー本体の機能**。生成プロジェクトには存在せず、**ビルダーが生成時にチェックする**予防ライブラリ
- 下流のハマりどころで「これはこのスタックを使う人全員が踏む」と分かったものを、ビルダーを触る時に `knowledge/` へ昇格させると、次の生成から予防される(ループが閉じる)

### どの箱に書くか(判断ルール)

「失敗・予防・ノウハウ」を入れる箱は複数ある。**内容ではなく「消費する人 × タイミング」で決める**と、`.env が読まれない` のように同じ話題が複数の箱に出てきても矛盾しない。

まず① **「コマンド/バージョンで再現する技術事実」か「人の判断・商習慣で変わるもの」か**で分ける:

- 判断・商習慣なら → `domain-knowledge.md`(Pro 版のみ存在。ここで終わり。技術事実は持ち込まない)
- 個人の事実・振る舞いなら → `aboutme.md` / `ai-behavior.md`

技術事実なら、② **「生成する瞬間に生成物へ焼けるか」** で3分岐:

| 箱 | 消費する人 | タイミング | `.env` の例 |
|---|---|---|---|
| `knowledge/{stack}.md` | ビルダー本体 | 生成する瞬間に読み、予防を生成物に焼く(生成物には存在しない) | `wrangler dev` は `.env` を読まない → `.dev.vars` を `.gitignore`+README に焼く |
| `.claude/rules/{topic}.md` | 生成物の中のAI | その作業に入った時トリガーで読む(生成物に存在する) | ルーチンは `.env` を読まない → Cloud Env に登録 / 秘密の中身に触れない |
| `## ハマりどころ` | 生成物の中のAI | そのプロジェクトで踏んだ後に記録 | そのプロジェクト固有の罠 |

`knowledge/` と `rules/` の違いは**「生成時に1回焼けるか / 作業時に読ませるか」**。`.dev.vars` が `knowledge/` なのは生成時に `.gitignore` 1行+README 1行で焼けるから。ルーチンの env が `rules/` なのは、ルーチンはまだ存在せず後でユーザーが実装作業に入った時に読ませる手順だから。

下流の `## ハマりどころ` で「このスタックを使う人全員が踏む」と分かったものは、ビルダーを触る時に `knowledge/{stack}.md` へ**昇格**させる(ループが閉じる)。

## 参照のしかた(ビルダー向け)

- 生成するプロジェクトのスタックが決まったら、**該当するファイルだけ**を参照する
- `.claude/rules/{topic}.md`(生成物側の「その作業の時だけ参照する」)と同じ思想。関係ないスタックのノウハウは持ち込まない

## 環境構築コンポーネントとして使う(レシピは「参照」する・インラインしない)

レシピの環境構築工程(`§2 スタック` / `§5 Phase 0 土台`)は、**手順をレシピ本文にベタ書きしない**。共通の構築手順は `knowledge/{stack}.md` に置き、レシピは**参照だけ**する。同じ wp-env / n8n / pnpm の構築が複数レシピに重複展開されると、片方だけ古くなって陳腐化する事故が起きるため。

- **置く中身**: 各 `{stack}.md` は「**セットアップ(構築手順)** + **地雷/予防**」の両方を持つ(現状の `## 必須予防策` / `## 接続方法` / `## 大前提` 等がこれにあたる)。レシピ §6 の「スタック共通地雷」もここへ集約(レシピ §6 は**そのレシピ固有のコード地雷だけ**)。
- **レシピ側の書き方**: §2 スタック表の備考や §5 Phase 0 で `knowledge/{stack}.md` を参照する(例: notion-wp §6 冒頭「環境の地雷は `knowledge/wp-env.md` に集約」/ §2 で `pnpm` 行 → `knowledge/pnpm.md`)。レシピは「**何を採用するか**」だけ決め、「**どう建てるか**」はコンポーネントに委譲する。
- **切り出す目安(rule of two)**: 1 本目のレシピは Phase 0 にインラインで書いてよい。**2 本目のレシピが同じ構築を要求した時点で `knowledge/{stack}.md` へ切り出し、両方を参照に置き換える**(早すぎる抽象化を避ける)。
- **docker 単体の扱い**: 現状 docker は `wp-env.md` 内(= wp-env の docker)に畳んである。n8n + docker など別文脈で docker-compose 構築の再利用が出たら `knowledge/docker.md` を独立させる(rule of two)。

## 配布

`knowledge/`(共通コツ)と `usecase/`(用途別仕様)は **Free / Pro 両方の配布物に含める**(pnpm の地雷は両版のユーザーが踏むため)。`scripts/build-dist.sh` の include 配列と `scripts/release-test.sh` の必須ファイルに登録済み。**`recipes/`(在庫レシピ)は許可リスト方式で同梱**(2026-06-20 改訂。Free=`FREE_RECIPES` の無料サンプル1本 / Pro=`PRO_RECIPES` カタログ、いずれも verified のみ)── 丸ごとコピーはせず、載せたファイルだけを個別コピー + マーカー処理 + シークレット走査で通すため、固有値/個人データの混入が構造的に起きない。
