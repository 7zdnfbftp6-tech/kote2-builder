# n8n — 生成時ノウハウ

**適用条件**: ユーザーが自動化基盤に n8n を指定している構成のとき(`aboutme.md` / `ai-behavior.md` に「自動化は n8n で」等)。

> n8n 2.14 系で確認(2026-06 検証)。

---

## 接続方法(どの経路でもワークフローの作成・編集ができる)

### ⚠ まずバージョンを確認する

n8n の **instance-level MCP がワークフローの「新規作成」「更新」に対応するのは n8n 2.14.0 以降**(ベータでリリース。クラウド / セルフホスト・コミュニティ / エンタープライズ いずれも利用可)。それ以前は**実行のみ**で、作成・編集はできない。

- **2.14.0 以降** → MCP 経路(A / B)で作成・編集できる
- **2.14.0 未満** → MCP では作れない。**REST 経路(C)を使う**か、インスタンスをアップグレードする

> 出典: n8n community「Create workflows via MCP」 https://community.n8n.io/t/create-workflows-via-mcp/280856

### 経路の選び方

バージョン要件を満たす前提で、生成プロジェクトの文脈に合わせて選ぶ:

| 経路 | 向く場面 | セットアップ | 前提 |
|---|---|---|---|
| **A. instance-level MCP**(設計・開発に推奨) | Claude が対話的にワークフローを設計・構築 | n8n インスタンスの MCP を Claude に接続(トークン) | n8n 2.14.0 以降 |
| **B. Claude の n8n コネクタ** | すでに Claude に n8n コネクタを繋いでいれば、それ経由で最も手軽 | コネクタを有効化(対話認証) | n8n 2.14.0 以降 |
| **C. REST API + API キー** | スクリプト / ヘッドレス / 定時実行、または **2.14.0 未満**の文脈 | キーを環境変数で(下記) | バージョン不問 |

- **設計・開発フェーズ**は A か B(MCP 系)が楽。
- **ヘッドレスや定時で叩く**必要があるなら C(キー)。対話認証(B、場合により A)は headless で動かないことがある点だけ注意。

### API キー / トークンの安全な渡し方(経路 C、およびトークンを使う A で必須)

- **キーをチャットに貼らせない**。`.env`(または `~/.zshrc`)に空の値を先に書き、ユーザー本人に記入させる:
  ```
  N8N_API_KEY=      # ← n8n の Settings > n8n API で発行して記入
  N8N_BASE_URL=     # ← https://{あなたの-n8n}
  ```
- スキル/スクリプトは環境変数から読む。`.env` は `.gitignore` に入れる(`@.claude/rules/secrets.md` に従う)。

## ワークフロー構築の定石

**共通の鉄則**: typeVersion / ノード構造を**推測しない**。一発で通そうとせず、作ったら読み戻して検証してから有効化する(バージョン不一致・パラメータ構造違いが一番の地雷)。

**MCP / コネクタ(SDK)経由(A / B)**:
1. `get_sdk_reference` で SDK パターンを確認
2. `search_nodes` で使うノードを探す
3. **`get_node_types` で正しい typeVersion とパラメータ定義を取得**(ここを飛ばして推測しない ← 最大の地雷)
4. コードを書いて `validate_workflow` → エラーが消えるまで直す
5. `create_workflow_from_code` で作成(更新は update 系)

**REST API 経由(C)**:
1. typeVersion / 構造が不明なら、同種ノードを使う**既存ワークフローを `GET /workflows/:id` で取得して構造を写す**
2. `POST /workflows`(新規)/ `PUT /workflows/:id`(更新)
3. `GET /workflows/:id` で読み戻して検証
4. `POST /workflows/:id/activate` で有効化(作成だけでは動かない)

## dify 連携

n8n から dify を使う場合は、専用ノードではなく **HTTP Request ノードで dify の API を叩く**のが基本(dify のワークフロー/チャット API エンドポイント + API キー)。dify のキーも上記と同じく環境変数で扱い、チャットに貼らせない。

---

## 設計フェーズ vs 運用フェーズ(棲み分け)

- **設計・開発(Claude が作る)**: MCP / コネクタ / REST で作成・編集・検証する
- **定時実行(運用で回す)**: n8n 本体の Schedule Trigger / Webhook に寄せる。**対話認証の MCP / コネクタは headless で動かない**ため、定時で回す処理を対話認証に依存させない

## 品質チェック(生成後)

- [ ] MCP 経路を使う場合、対象 n8n が **2.14.0 以降**か確認した(未満なら REST 経路)
- [ ] 経路に応じた接続が設定されている(MCP 接続 / n8n コネクタ / API キー のいずれか)
- [ ] キー・トークンを使う場合、環境変数化され `.env` が `.gitignore` に入っている。チャットで受け取っていない
- [ ] ワークフロー作成後に検証(`validate_workflow` or `GET` 読み戻し)してから有効化している
- [ ] 定時実行を伴う場合、対話認証ではなく n8n 側の Schedule / Webhook に寄せている
